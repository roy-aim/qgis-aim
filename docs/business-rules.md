# Aturan Bisnis — AIM Editor (QGIS Plugin)

## 1. Latar Belakang dan Tujuan

Organisasi memiliki basis data geospasial (PostGIS, database `aimdb`) yang menyimpan data infrastruktur kebandarudaraan mengikuti model data AIS/ICAO. Entitas induk (*parent*) adalah tabel **`adhp`** (Aerodrome/Heliport — merepresentasikan bandara), dengan primary key `gfid` (`VARCHAR(38)`, string UUID kustom berformat `{UPPERCASE-GUID}`, bukan tipe `uuid`/`integer` native PostgreSQL).

Sejumlah entitas anak (*child*) yang berelasi ke `adhp` tersimpan **bukan sebagai tabel masing-masing**, melainkan sebagai baris di dalam tabel geometri generik yang dibedakan lewat kolom `SUBTYPE_CODE`. Cakupan awal plugin ini adalah tabel **`ADHPSurfaceArea`** (geometri polygon, SRID 4326), yang mencakup 10 jenis subtipe (Runway, RunwayProtection, FATO, FATOProtection, TLOF, TLOFProtection, Taxiway, Stopway, Apron, BlastPad — lihat Bagian 9 untuk detail lengkap), di mana **hanya subtipe Taxiway (`SUBTYPE_CODE = 6`) dan Apron (`SUBTYPE_CODE = 8`) yang menjadi cakupan pengeditan plugin ini**. Foreign key ke parent bernama `ADHP_ID`, menunjuk ke `adhp.gfid`.

Basis data ini adalah **database yang sama** yang dipakai backend REST API existing (lihat Bagian 1.1) — bukan instance terpisah.

Organisasi sudah memiliki sistem otorisasi (manajemen pengguna, peran, dan hak akses) yang independen secara konsep dari data GIS, namun secara fisik berbagi database yang sama, diimplementasikan sebagai REST API dengan mekanisme autentikasi berbasis token **PASETO**.

Tujuan dari plugin **AIM Editor** adalah menyediakan jalur kerja yang terkendali bagi pengguna untuk mengedit geometri layer-layer tertentu di PostGIS, tanpa mengandalkan Browser Panel atau Layer Panel bawaan QGIS yang bersifat bebas-akses, sekaligus tetap memanfaatkan perkakas *digitizing* native QGIS (snapping, undo/redo, form atribut). Plugin ini dirancang agar entitas baru (subtipe lain, atau tabel geometri AIS/ICAO lain di luar `ADHPSurfaceArea`) dapat ditambahkan secara **inkremental satu per satu** di iterasi mendatang, mengikuti pola arsitektur yang sama — **bukan** mendukung seluruh entitas AIS/ICAO sekaligus sejak rilis awal.

### 1.1 Tentang Backend REST API Existing

Backend REST API (repositori terpisah `backend-aim`, ditulis dengan Go + Gin + pgx, migrasi skema dikelola `golang-migrate`) sudah menyediakan:
- Autentikasi berbasis token **PASETO v2 mode local/symmetric** (payload **terenkripsi**, bukan hanya ditandatangani — plugin tidak dapat dan tidak perlu men-decode isinya sendiri).
- Endpoint login (`POST /auth/login`) dan endpoint profil pengguna aktif (`GET /me`, sudah mencakup `roles` dan `permissions`).
- Model otorisasi berbasis `users` → `user_roles` → `roles` → `role_permissions` → `permissions`, dengan nama permission bergaya `resource:action` (mis. `runway:read`, `adhp:update`). **Model ini bersifat flat dan global per pengguna** — tidak ada kolom/konsep cakupan (*scope*) seperti per-bandara atau per-wilayah pada skema `roles`/`permissions` manapun.
- Endpoint CRUD existing untuk `adhp` (`internal/adhp/`) dan untuk `ADHPSurfaceArea` (di dalam modul `internal/runway/`, karena `ADHPSurfaceArea` mencakup keluarga "runway complex"). Endpoint-endpoint ini **tidak dipakai** oleh plugin untuk operasi tulis geometri (lihat Prinsip Utama, Bagian 2) — plugin menulis langsung ke PostGIS secara native. Endpoint ini disebut di sini semata sebagai konteks bahwa REST API dan skema datanya sudah saling terhubung secara nyata, bukan asumsi.
- Belum ada endpoint yang memetakan pengguna ke kredensial PostgreSQL untuk keperluan akses native — ini yang menjadi endpoint **baru** yang perlu ditambahkan (`GET /db-credentials`, lihat Bagian 3.2).

## 2. Prinsip Utama

1. **Pemisahan identitas aplikasi dan identitas basis data.** Pengguna login menggunakan akun aplikasi (REST API), bukan kredensial PostgreSQL secara langsung. Kredensial PostgreSQL diperoleh secara otomatis oleh plugin setelah otorisasi berhasil.
2. **Kredensial basis data bersifat granular per kelompok hak akses (role-scoped), bukan akun bersama tunggal untuk semua orang.** Setiap kombinasi hak akses aplikasi dipetakan ke satu peran PostgreSQL dengan hak akses (grant) yang sesuai cakupannya. Kebocoran satu kredensial peran tidak boleh memberi akses penuh ke seluruh data.
3. **Editing geometri dilakukan secara native QGIS↔PostGIS**, bukan melalui REST API, agar pengguna tetap mendapat pengalaman *digitizing* standar QGIS (snapping, transaksi edit, undo/redo). Otorisasi dan proteksi data dijembatani melalui REST API dan diperkuat lewat kontrol di level basis data.
4. **Akses ke layer dibatasi sesuai hak (rights) pengguna** yang diperoleh dari REST API. Layer/subtipe yang tidak diizinkan tidak boleh dimuat/ditampilkan/dapat diedit oleh pengguna.
5. **Navigasi data dilakukan melalui pencarian terarah (search), bukan penjelajahan bebas (browsing).** Pengguna mencari bandara (*parent*, tabel `adhp`) melalui ICAO, IATA, atau nama, lalu bekerja dalam konteks bandara tersebut.
6. **Penambahan entitas baru dilakukan secara inkremental.** Rilis awal plugin hanya mencakup satu tabel (`ADHPSurfaceArea`) dengan dua subtipe (Apron, Taxiway). Entitas/subtipe lain ditambahkan satu per satu di iterasi mendatang, bukan dirancang untuk mendukung seluruh skema AIS/ICAO sejak awal.

## 3. Aturan Otorisasi dan Kredensial

### 3.1 Alur Login
- Pengguna login ke plugin menggunakan kredensial aplikasi (`login_id` — dapat berupa username atau email — dan password) melalui dialog kustom, bukan dialog koneksi database bawaan QGIS.
- Plugin memanggil `POST /auth/login` pada REST API existing dan menerima **token PASETO v2 (mode *local*)** dalam field `token` pada response (bentuk string `v2.local.xxxxx...`).
- Plugin **tidak men-decode isi token** (dan secara teknis tidak bisa, karena mode *local* terenkripsi simetris dengan kunci yang hanya dipegang server); token diperlakukan sebagai *bearer token* buram (opaque) yang dilampirkan pada setiap permintaan berikutnya ke REST API.

### 3.2 Endpoint Kredensial Basis Data (`GET /db-credentials`)
- Endpoint ini adalah endpoint **baru** yang harus disediakan di sisi server backend (`backend-aim`) — belum ada saat ini.
- Alur kerja endpoint di sisi server:
  1. Verifikasi keabsahan token PASETO yang dikirim pada header `Authorization` (memakai `AuthMiddleware` existing).
  2. Ekstrak `permissions` pengguna — **bukan** lewat decode klaim token secara manual (token hanya membawa `RoleIDs`, bukan daftar permission), melainkan dengan memanggil ulang logic yang sama dipakai `GET /me` (`permission.Service.GetForRoles(roleIDs)`).
  3. Petakan kombinasi permission tersebut ke **satu peran PostgreSQL** yang sesuai. **Logic pemetaan ini murni baru** — tidak ada tabel/skema existing di backend yang merepresentasikan pemetaan permission-ke-role-PostgreSQL; ini perlu didesain dan disimpan sebagai bagian dari endpoint baru ini. Plugin **tidak** memakai permission `runway:*` existing (cakupannya terlalu luas, meliputi seluruh subtipe `ADHPSurfaceArea` termasuk Runway yang di luar cakupan plugin) — backend menambahkan permission baru khusus: `qgis-apron-taxiway:read` dan `qgis-apron-taxiway:update`, dipetakan ke peran PostgreSQL `qgis_reader_apron_taxiway` dan `qgis_writer_apron_taxiway`. **Detail lengkap desain permission/role baru ini didokumentasikan terpisah di repositori backend**: `backend-aim/docs/aim-pages/qgis-support/qgis-be-business-rules.md` dan `qgis-be-implementation-plan.md` — dokumen ini tidak menduplikasi detailnya.
  4. Kembalikan kredensial peran PostgreSQL tersebut ke plugin: host, port, nama database, username, password, dan waktu kedaluwarsa (`expires_at`).
- Kredensial dapat bersifat **statis** (dibuat manual per peran, disimpan sebagai *secret* di server) pada fase awal implementasi, dengan opsi peningkatan ke kredensial **dinamis/berumur pendek** (short-lived) di fase berikutnya, misalnya menggunakan `ALTER ROLE ... VALID UNTIL` atau Vault Database Secrets Engine.
- **Cakupan (scope) rilis awal: per jenis layer/subtipe, bukan per bandara/wilayah.** Sistem permission backend existing bersifat flat dan global per pengguna (tidak ada kolom/konsep scope seperti per-bandara pada skema `roles`/`permissions`/`role_permissions` manapun). Oleh karena itu, keputusan sadar untuk rilis awal: peran PostgreSQL dan kebijakan RLS (lihat Bagian 6) membatasi akses berdasarkan **jenis data** (mis. peran `qgis_writer_apron_taxiway` boleh mengedit baris `ADHPSurfaceArea` dengan `SUBTYPE_CODE` 6 atau 8 di **seluruh** bandara, tapi tidak subtipe lain seperti Runway), **bukan** dibatasi ke bandara tertentu. Pembatasan per-bandara/wilayah membutuhkan skema baru di backend (mis. tabel mapping pengguna-ke-bandara) yang **tidak** dikerjakan pada rilis awal ini.
- Host, port, dan nama database yang dikembalikan endpoint ini mengacu ke instance PostGIS yang sama dengan `DATABASE_URL` yang sudah dipakai backend (lihat `config/db.go` di `backend-aim`) — endpoint baru ini menambahkan *pemetaan pengguna ke role PostgreSQL* pada database yang sama, bukan menghubungkan ke database terpisah.
- **Granularitas peran PostgreSQL: satu peran per kelompok hak akses (grup), bukan per pengguna aplikasi individu.** Artinya seluruh pengguna aplikasi yang memiliki kombinasi permission yang sama akan berbagi satu kredensial peran PostgreSQL yang sama (mis. `qgis_writer_apron_taxiway`).
  - **Peran PostgreSQL yang dikembalikan endpoint ini tidak boleh berupa peran pemilik skema database.** Peran pemilik skema memiliki hak akses penuh tanpa batas dan lazimnya kebal (*bypass*) terhadap Row-Level Security, sehingga penggunaan peran ini oleh plugin akan meniadakan seluruh mitigasi keamanan di Bagian 6. Peran pemilik skema hanya dipakai untuk keperluan administratif/migrasi skema di luar plugin ini.
  - **Karena database yang sama juga menyimpan tabel otorisasi backend (`users`, `roles`, `permissions`, `role_permissions`, dst.), peran PostgreSQL yang dipetakan untuk plugin WAJIB diberi grant secara eksplisit hanya ke tabel-tabel GIS yang relevan** (mis. `ADHPSurfaceArea`, `adhp` untuk keperluan baca/pencarian parent). Peran ini tidak boleh punya akses baca/tulis ke tabel-tabel otorisasi backend sama sekali, walaupun berada di database yang sama.
  - **Konsekuensi model berbagi-peran (shared role):** identitas *individu* pengguna aplikasi tidak dapat dibedakan dari sisi PostgreSQL semata (mis. `current_user`, `pg_stat_activity`) karena banyak pengguna memakai peran PostgreSQL yang sama. Identifikasi individu **sepenuhnya bergantung** pada kolom audit `last_edited_user` (lihat Bagian 6 dan Bagian 7 — nilai ini disadari dapat dipalsukan jika pengguna melakukan bypass terhadap plugin).
  - Model alternatif (satu peran PostgreSQL per pengguna aplikasi individu) sengaja **tidak dipilih** untuk saat ini karena kompleksitas operasional yang jauh lebih tinggi. Dapat dipertimbangkan ulang di masa depan jika kebutuhan audit granular per individu menjadi kritis.

### 3.3 Penyimpanan Kredensial di Sisi Klien
- Kredensial basis data **tidak boleh** disimpan sebagai variabel biasa, file konfigurasi biasa, atau dalam bentuk teks polos (plaintext) dalam bentuk apa pun yang persisten.
- Kredensial disimpan melalui **QGIS Authentication Manager** (`QgsAuthManager` beserta `QgsAuthMethodConfig`), yang menyimpan data secara terenkripsi (AES) di `qgis-auth.db` milik QGIS.
- Layer PostGIS dibuka menggunakan `QgsDataSourceUri.setAuthConfigId(config_id)`, **bukan** `setUsername()`/`setPassword()` langsung, sehingga password tidak pernah tampil dalam bentuk teks polos di panel Layer Properties > Source maupun dalam berkas proyek QGIS (.qgz/.qgs).
- Konfigurasi autentikasi (`authcfg`) wajib dihapus (`removeAuthMethodConfig`) pada saat: plugin di-*unload*, pengguna logout, atau QGIS ditutup — untuk mencegah kredensial basis data tertinggal di `qgis-auth.db` melebihi masa sesi.

### 3.4 Perpanjangan Sesi (Session Renewal)
- Jika `expires_at` dari kredensial basis data mendekati waktu kedaluwarsa sementara pengguna masih dalam sesi pengeditan aktif, plugin harus memperbarui kredensial dengan memanggil ulang endpoint `/db-credentials` menggunakan token yang masih berlaku.
- Kredensial baru diterapkan dengan memperbarui (`updateAuthenticationConfig`) konfigurasi autentikasi yang **sama** (config_id tidak berubah), sehingga layer yang sudah dimuat di kanvas **tidak perlu** dimuat ulang (reload).

## 4. Aturan Akses Layer dan Data

### 4.1 Pemuatan Layer Berdasarkan Hak Akses
- Hanya layer/subtipe yang termasuk dalam hak akses (rights) pengguna yang dimuat ke dalam proyek QGIS oleh plugin.
- Sumber hak akses adalah endpoint **existing** `GET /me` pada backend (bukan endpoint baru terpisah) — field `permissions` pada response-nya berisi array string bergaya `resource:action`. Untuk rilis awal, plugin memeriksa keberadaan permission khusus `qgis-apron-taxiway:read`/`qgis-apron-taxiway:update` (permission baru, ditambahkan backend khusus untuk plugin ini — **bukan** memakai permission `runway:*` existing yang cakupannya lebih luas, lihat `backend-aim/docs/aim-pages/qgis-support/qgis-be-business-rules.md` Bagian 3.1) untuk menentukan apakah layer Apron/Taxiway boleh dimuat, dan apakah dalam mode baca-saja atau dapat diedit.
- Browser Panel dan Layer Panel bawaan QGIS **tidak digunakan** sebagai jalur utama untuk membuka layer; pengguna berinteraksi melalui antarmuka kustom plugin.
- Layer/subtipe di luar cakupan hak akses pengguna tidak boleh terlihat maupun dapat diakses melalui plugin.

### 4.2 Konteks Data Induk (Parent Airport)
- Pengguna wajib memilih satu bandara (*parent*, tabel `adhp`) sebagai konteks kerja sebelum dapat mengedit data anak (*child*).
- Pemilihan bandara dilakukan melalui dialog pencarian (search) berdasarkan kolom `icao_txt`, `iata_txt`, atau `name_txt` pada tabel `adhp` — bukan melalui penjelajahan tabel secara manual.
- Query pencarian terhadap tabel `adhp` **wajib terparameterisasi** untuk mencegah SQL injection.
- Nilai kunci yang dipakai untuk konteks kerja adalah `adhp.gfid` (`VARCHAR(38)`) — **bukan** integer/uuid native. Seluruh ekspresi filter dan default value pada child layer harus memperlakukan nilai ini sebagai string.

### 4.3 Pemfilteran Data Anak (Child Layers)
- Layer child untuk rilis awal (Apron dan Taxiway) **bukan dua tabel/layer QGIS yang independen** — keduanya adalah baris dari tabel `ADHPSurfaceArea` yang sama, dibedakan lewat kolom `SUBTYPE_CODE` (Apron = 8, Taxiway = 6).
- Setelah bandara dipilih, layer/tampilan child difilter menggunakan `setSubsetString()` dengan kondisi gabungan: `ADHP_ID = '<gfid bandara terpilih>' AND SUBTYPE_CODE IN (6, 8)` — atau difilter terpisah per subtipe jika didesain sebagai dua entri layer berbeda di panel plugin (satu untuk Apron, satu untuk Taxiway) yang keduanya bersumber dari tabel `ADHPSurfaceArea` yang sama dengan filter `SUBTYPE_CODE` berbeda. Keputusan desain UI (satu layer gabungan vs dua layer terpisah per subtipe) didetailkan di `docs/implementation-plan.md`.
- Subtipe lain di `ADHPSurfaceArea` (Runway, RunwayProtection, FATO, FATOProtection, TLOF, TLOFProtection, Stopway, BlastPad) **tidak dimuat sebagai layer yang dapat diedit** oleh plugin pada rilis awal ini. Pembatasan ini ditegakkan berlapis: plugin hanya memuat subtipe 6/8 (lapisan UX), dan RLS di database membatasi peran PostgreSQL plugin ke `SUBTYPE_CODE IN (6, 8)` secara mutlak (lapisan keamanan sesungguhnya, lihat Bagian 6) — bukan bergantung pada permission aplikasi mana pun yang dipegang pengguna.
- Kanvas peta secara otomatis melakukan zoom ke *extent* bandara yang terpilih setelah pemfilteran (extent diambil dari kolom `shape` pada `adhp`, yaitu titik lokasi bandara, dengan buffer yang memadai — bukan dari extent gabungan fitur anak yang mungkin masih kosong pada bandara baru).
- Saat pengguna berganti bandara, filter pada seluruh layer anak yang aktif harus diperbarui secara konsisten (tidak boleh ada layer yang tertinggal dengan filter bandara sebelumnya).

### 4.4 Pengisian Kunci Asing (Foreign Key) dan Subtype Otomatis
- Saat pengguna menambahkan fitur (geometri) baru pada layer anak, kolom kunci asing (`ADHP_ID`) **wajib terisi otomatis** sesuai `gfid` bandara yang sedang aktif, menggunakan `QgsDefaultValue`, dengan nilai berupa string (bukan ekspresi numerik).
- Kolom `SUBTYPE_CODE` **juga wajib terisi otomatis** sesuai konteks layer yang sedang diedit pengguna (6 untuk Taxiway, 8 untuk Apron) — bukan diinput manual oleh pengguna, untuk mencegah salah subtipe yang dapat membuat fitur baru justru masuk ke kategori Runway/subtipe lain yang seharusnya tidak dapat diedit lewat plugin ini.
- Nilai default `ADHP_ID` disetel ulang setiap kali pengguna berganti konteks bandara.
- Kolom `ADHP_ID` dan `SUBTYPE_CODE` pada form atribut sebaiknya bersifat **read-only**, agar tidak diubah secara manual oleh pengguna yang berpotensi merusak konsistensi relasi atau membuat fitur "berpindah" ke subtipe di luar cakupan plugin.

## 5. Aturan Pengeditan Geometri

- Pengeditan dan penambahan geometri dilakukan menggunakan perkakas *digitizing* standar QGIS (snapping, undo/redo berfungsi sebagaimana mestinya). Tipe geometri untuk Apron dan Taxiway adalah **polygon** (kolom `SHAPE`, `GEOMETRY(Polygon, 4326)`).
- Pengisian atribut non-geometri dilakukan melalui Attribute Form standar QGIS, dikonfigurasi lewat Layer Properties (field wajib, label, constraint diatur di level konfigurasi layer, bukan di-*hardcode* dalam plugin). Mengingat `ADHPSurfaceArea` memiliki lebih dari 40 kolom, form atribut untuk rilis awal sebaiknya hanya menonjolkan kolom yang relevan untuk Apron/Taxiway (mis. `DESIGNATOR_TXT`, `NAME_TXT`, `STATUS_CODE`, `LENGTH_VAL`/`WIDTH_VAL` bila relevan) dan menyembunyikan/mengelompokkan kolom lain yang tidak relevan lewat form kustom (Drag-and-Drop Designer di Layer Properties), bukan menampilkan seluruh kolom mentah.
- Proses simpan (commit) dilakukan **langsung secara native ke PostGIS**, bukan melalui REST API. Pertahanan utama terhadap potensi penyalahgunaan berada pada grant PostgreSQL per peran dan Row-Level Security (lihat Bagian 6), bukan pada validasi di level plugin semata.
- Kolom audit `created_user`, `created_date`, `last_edited_user`, `last_edited_date` **sudah ada di skema tabel `ADHPSurfaceArea`**, namun **tidak diisi otomatis oleh trigger database** (dikonfirmasi: tidak ada trigger audit di tabel ini). Plugin **wajib** mengisi `last_edited_user` (dan `last_edited_date`) secara eksplisit sebelum commit — lewat `QgsDefaultValue` pada `last_edited_date` (nilai waktu saat ini) dan `last_edited_user` (identitas pengguna aplikasi yang sedang login, bukan role PostgreSQL bersama). Untuk fitur baru, `created_user`/`created_date` mengikuti pola yang sama.

### 5.1 Penanganan Edit Bersamaan (Concurrent Edit)

- Strategi yang dipakai adalah **last-write-wins**, mengikuti perilaku default QGIS native editing (bukan locking eksplisit).
- **Alasan:** QGIS menahan perubahan edit di buffer memori lokal selama sesi editing (`startEditing()`) dan baru membuka transaksi singkat saat commit (`saveEdits()`). Tidak ada cara natural untuk menahan row-level lock PostgreSQL (`SELECT ... FOR UPDATE`) selama durasi sesi edit tanpa keluar dari pola *native* QGIS↔PostGIS yang menjadi keputusan arsitektur inti — dan kontensi edit pada geometri infrastruktur (apron/taxiway) diperkirakan rendah.
- Konsekuensi: jika dua pengguna mengedit fitur yang sama secara bersamaan, perubahan yang di-commit belakangan akan menimpa perubahan sebelumnya tanpa peringatan konflik di level plugin.
- Mitigasi yang tersedia: kolom audit `last_edited_user`/`last_edited_date` (lihat Bagian 6, poin Jejak Audit) memungkinkan penimpaan tersebut **terdeteksi setelah fakta** lewat riwayat kolom tsb, meski tidak mencegahnya secara real-time (dan bukan riwayat penuh/log, hanya nilai terakhir — lihat Bagian 6 soal keterbatasan ini karena tidak ada trigger/tabel audit log terpisah).
- **Di luar cakupan rilis awal:** mekanisme *soft lock* di level aplikasi (misalnya tabel `editing_locks` yang dicek REST API sebelum akses edit diberikan) dapat dipertimbangkan di iterasi mendatang jika kontensi edit terbukti menjadi masalah nyata di lapangan. Tidak dikerjakan di awal karena menambah kompleksitas signifikan tanpa bukti kebutuhan.

## 6. Aturan Keamanan Wajib (Mitigasi)

Karena kredensial basis data tetap berada di sisi klien (kelemahan inheren dari pola *native* QGIS↔PostGIS dibandingkan jalur *full-REST*), dan karena database yang dipakai plugin ini **sama** dengan database backend REST API (lihat Bagian 1.1), mitigasi berikut **wajib** diterapkan di sisi basis data/infrastruktur:

1. **Row-Level Security (RLS).** **Dikonfirmasi: belum ada satu pun kebijakan RLS di database ini saat ini** (tidak ditemukan `ENABLE ROW LEVEL SECURITY`/`CREATE POLICY` di migration manapun) — ini murni pekerjaan baru, bukan sesuatu yang sudah ada untuk "diaktifkan". RLS wajib diterapkan pada `ADHPSurfaceArea` berdasarkan `SUBTYPE_CODE`, sehingga peran PostgreSQL yang dipetakan untuk plugin (mis. `qgis_writer_apron_taxiway`) hanya dapat menulis baris dengan `SUBTYPE_CODE IN (6, 8)`, tidak subtipe lain. **Untuk rilis awal, cakupan RLS adalah per jenis layer/subtipe** (lihat Bagian 3.2), **bukan per wilayah/bandara**.
2. **Pembatasan Grant Eksplisit ke Tabel Otorisasi Backend.** Karena `ADHPSurfaceArea`/`adhp` berbagi database yang sama dengan tabel `users`/`roles`/`permissions`/`role_permissions` milik backend REST API, peran PostgreSQL yang dipetakan untuk plugin **wajib** hanya diberi grant ke tabel GIS yang relevan (lihat Bagian 3.2) — sama sekali tidak boleh memiliki hak akses (bahkan `SELECT`) ke tabel-tabel otorisasi backend tersebut.
3. **Jejak Audit (Audit Trail).** Skema `ADHPSurfaceArea` **sudah memiliki** kolom `created_user`, `created_date`, `last_edited_user`, `last_edited_date`, namun **tidak ada trigger DB** yang mengisinya otomatis (dikonfirmasi dari migration). Plugin bertanggung jawab mengisi kolom-kolom ini secara eksplisit sebelum commit (lihat Bagian 5). Ini **bukan** log audit lengkap (riwayat tiap perubahan) — hanya nilai terakhir. Trigger `AFTER INSERT/UPDATE/DELETE` yang mencatat riwayat perubahan lengkap ke tabel log terpisah **belum ada** dan merupakan peningkatan yang dapat dipertimbangkan di masa depan, bukan kebutuhan wajib rilis awal (dibedakan dari pengisian kolom `last_edited_user` yang sifatnya wajib).
   - Disadari dan diterima sebagai limitasi: nilai `last_edited_user` yang diisi dari sisi klien secara teknis dapat dipalsukan jika pengguna melakukan bypass terhadap plugin dan terhubung langsung ke basis data menggunakan kredensial yang sama.
4. **Pembatasan Jaringan.** Basis data PostGIS idealnya hanya dapat dijangkau dari jaringan internal/VPN, tidak terhubung langsung ke internet publik.
5. **Constraint Kunci Asing (Foreign Key) di Level Basis Data.** FK constraint `ADHPSurfaceArea.ADHP_ID → adhp.gfid` (sudah ada di skema existing, `fk_adhp_surface_area_adhp_id`) tetap dipertahankan sebagai lapisan pertahanan integritas relasi yang independen dari default value expression di level antarmuka pengguna.

## 7. Batasan yang Diketahui (Known Limitations)

- Nilai kolom audit (`last_edited_user`) yang diisi dari sisi klien secara teknis dapat dipalsukan oleh pengguna yang memiliki akses langsung ke kredensial peran PostgreSQL dan melakukan bypass terhadap plugin. Ini adalah limitasi yang **diterima secara sadar** dalam desain ini, dengan mitigasi berlapis (RLS, pembatasan jaringan) sebagai kompensasi.
- **Tidak ada riwayat audit lengkap** — kolom `last_edited_user`/`last_edited_date` hanya menyimpan nilai terakhir, bukan histori tiap perubahan. Kalau suatu saat perlu riwayat lengkap (mis. untuk investigasi insiden), itu memerlukan trigger + tabel log terpisah yang belum dikerjakan pada rilis awal.
- Kredensial basis data statis (fase awal) memiliki risiko lebih tinggi dibanding kredensial dinamis/berumur pendek. Peningkatan ke kredensial dinamis direncanakan sebagai perbaikan fase berikutnya, bukan kebutuhan pada rilis awal.
- **Kredensial basis data dapat tertinggal di `qgis-auth.db` lebih lama dari masa sesi normal jika QGIS berhenti secara tidak normal (crash/force-quit),** karena proses pembersihan config (`removeAuthMethodConfig`, lihat Bagian 3.3) hanya berjalan pada alur *unload*/logout/penutupan QGIS yang normal. Dengan kredensial statis (tanpa `expires_at` singkat), kredensial yang tertinggal ini tetap valid tanpa batas waktu sampai dicabut manual oleh admin. **Diterima secara sadar sebagai risiko fase awal** — dampaknya dibatasi karena kredensial bersifat per-kelompok-hak-akses dengan scope RLS terbatas (lihat Bagian 3.2), bukan akses penuh ke seluruh data.
- **Source code plugin sengaja tidak di-obfuscate/di-compile.** QGIS plugin secara praktis harus berupa Python biasa (`.py`) agar dapat di-load QGIS; opsi "compile" (`.pyc`, PyInstaller, Nuitka, dsb.) hanya menaikkan effort membaca kode, bukan mencegahnya secara sungguhan (bytecode Python dapat di-decompile), dan mengubah cara instalasi plugin secara signifikan. Keputusan ini diambil secara sadar karena pertahanan yang sesungguhnya terhadap penyalahgunaan tidak bergantung pada kerahasiaan source code plugin, melainkan pada kontrol di level basis data (RLS, grant per peran, lihat Bagian 6) — kredensial basis data tidak pernah tertanam (*hardcoded*) di source code, sehingga membaca source code plugin tidak memberi akses tambahan apa pun kepada siapa pun yang tidak sudah memiliki akses ke `qgis-auth.db` miliknya sendiri.
## 8. Distribusi dan Pembaruan Plugin

- Plugin didistribusikan melalui **QGIS Plugin Repository kustom** (bukan repo resmi QGIS.org), mengingat plugin ini spesifik internal organisasi.
- Repository kustom diimplementasikan lewat file `plugins.xml` yang mengarah ke berkas rilis (`.zip`) yang di-hosting di **GitHub Releases** pada repositori plugin ini (repositori bersifat publik).
- **Klarifikasi model visibilitas (dua lapisan independen):**
  - *Source code dan rilis `.zip` bersifat publik* di GitHub (siapa pun bisa melihat/mengunduh) — ini diterima sebagai keputusan sadar (lihat Bagian 7 soal alasan tidak melakukan obfuscation) karena tidak ada kredensial atau secret apa pun yang tertanam di kode.
  - *Plugin **tidak** didaftarkan ke QGIS Official Plugin Repository (katalog resmi QGIS.org)*, sehingga tidak akan "ditemukan" lewat pencarian normal di Plugin Manager oleh siapa pun yang tidak mengetahui URL `plugins.xml` khusus organisasi ini secara eksplisit dan menambahkannya secara manual. Ini bersifat *practical obscurity* pada lapisan distribusi, bukan kontrol akses yang sesungguhnya.
  - **Kontrol akses yang sesungguhnya** tetap berada di lapisan otorisasi: plugin tidak berfungsi tanpa akun REST API organisasi yang valid (lihat Bagian 3). Seseorang yang berhasil menginstal plugin ini di luar organisasi tetap tidak dapat memakainya secara berarti tanpa kredensial aplikasi yang sah.
- Pengguna menambahkan URL repository kustom tersebut sekali di QGIS Plugin Manager (Settings > Plugins > Settings > Plugin Repositories); setelahnya QGIS Plugin Manager secara otomatis memberi notifikasi dan mekanisme instal-ulang saat versi baru dirilis (perilaku bawaan QGIS, bukan kode kustom buatan plugin ini).
- **Alasan tidak membuat mekanisme self-update kustom** (mis. plugin men-download dan mengganti file sendiri): mekanisme auto-update kustom menambah permukaan serangan (attack surface) yang tidak perlu untuk plugin yang berinteraksi dengan kredensial basis data, tanpa keuntungan berarti dibanding memakai mekanisme QGIS Plugin Repository yang sudah teruji dan dipercaya secara luas.
- Repositori backend REST API tetap **privat** dan terpisah dari repositori plugin ini. Plugin hanya bergantung pada `base_url` REST API (dikonfigurasi via `QSettings`, lihat implementation-plan.md Tahap 2) dan kontrak API publik (endpoint, format request/response) — tidak bergantung pada source code backend.
- Karena backend REST API masih dalam pengembangan aktif dan dapat berubah kontraknya, plugin sebaiknya melakukan pengecekan kompatibilitas versi terhadap backend saat startup (lihat implementation-plan.md untuk detail teknis), agar pengguna mendapat pesan yang jelas ("plugin perlu diperbarui") alih-alih error teknis yang membingungkan saat terjadi ketidakcocokan versi.

## 9. Ruang Lingkup Awal (Scope Rilis Pertama)

- Entitas *parent*: tabel **`adhp`** (kolom kunci: `gfid` [PK, `VARCHAR(38)`], `icao_txt`, `iata_txt`, `name_txt`, `shape` [`GEOMETRY(PointZ, 4326)`]).
- Entitas *child*: tabel **`ADHPSurfaceArea`** (kolom kunci: `GFID` [PK, `VARCHAR(38)`], `ADHP_ID` [FK ke `adhp.gfid`], `SUBTYPE_CODE`, `SHAPE` [`GEOMETRY(Polygon, 4326)`]), **dibatasi hanya pada dua subtipe**:
  - `SUBTYPE_CODE = 6` → **Taxiway**
  - `SUBTYPE_CODE = 8` → **Apron**
- Subtipe lain pada `ADHPSurfaceArea` yang **secara eksplisit di luar cakupan** rilis awal (tidak dapat dilihat/dimuat/diedit lewat plugin ini): 0=Runway, 1=RunwayProtection, 2=FATO, 3=FATOProtection, 4=TLOF, 5=TLOFProtection, 7=Stopway, 9=BlastPad.
- Tabel geometri AIS/ICAO lain yang berelasi ke `adhp` (mis. `ADHPSurfacePoint`, `ADHPSurfaceLine`, `Marking`, dan domain lain seperti runway threshold, navaid, airspace, dst.) **di luar cakupan rilis awal**, dan akan dipertimbangkan untuk ditambahkan **satu per satu** pada iterasi mendatang mengikuti pola arsitektur yang sama (lihat Bagian 2, Prinsip Utama poin 6) — bukan dikerjakan sekaligus.
